# PostgreSQL

## Схема

`sessions`: UUID `id`, уникальный `token_hash`, `created_at`, `expires_at`, `next_sequence`. Срок сессии фиксирован: создание + 1 час. Секретный cookie-токен никогда не хранится открытым.

`messages`: UUID `id`, FK `session_id`, монотонный `sequence` с нуля, `role`, `content`, `status`, UUID `request_id`, `created_at`, `expires_at`, `updated_at`. Срок каждого сообщения — создание + 6 часов; частичное или финальное сохранение его не продлевает. Роли: user/assistant; статусы: complete/generating/interrupted/error. Пользовательская запись всегда complete. Внешний ключ RESTRICT: истечение сессии не удаляет историю каскадом.

`schema_migrations(version, applied_at)` хранит применённые версии.

## Индексы и ограничения

- PK обеих таблиц, UNIQUE token_hash.
- UNIQUE `(session_id, sequence)` одновременно индекс истории и защита порядка.
- UNIQUE `(session_id, request_id, role)` связывает одну пару user/assistant без дубликатов.
- Частичный UNIQUE `(session_id) WHERE status='generating'`: не более одной генерации даже между процессами.
- `sessions(expires_at)`, `messages(expires_at)` для TTL.
- Частичный `(session_id, sequence DESC) WHERE status='complete'` для контекста.
- Частичный `messages(updated_at) WHERE status='generating'` для восстановления.
- CHECK для ролей, статусов, неотрицательных последовательностей и положительного срока хранения.

## Миграции

```sh
DATABASE_URL=postgresql://... pnpm --filter @gate/api migrate
```

CLI загружает корневую .env; значение DATABASE_URL из окружения приоритетнее. `migrate(pool)` применяет миграцию 1 в транзакции под advisory-lock: повторный запуск и одновременные старты безопасны. Производственный сервер также применяет миграции перед listen. Новые изменения оформлять новой версией, не редактировать применённую миграцию 1. Автоматического downgrade нет.

## Генерация и согласованность

Короткая транзакция блокирует строку активной сессии (`FOR UPDATE`), проверяет срок и requestId, сохраняет user/assistant, резервирует два sequence, выбирает контекст, затем COMMIT. Сеть к ИИ начинается уже после освобождения соединения. Повтор того же requestId с другим текстом — 409. Повтор завершённого запроса воспроизводит сохранённый результат без нового обращения к ИИ; активный дубль — 409.

Периодический flush обновляет content и heartbeat updated_at раз в секунду. Финальная запись обновляется только из generating. История и контекст сразу исключают просроченные записи, независимо от физической очистки.

## Восстановление и очистка

На старте и раз в минуту generating-записи без heartbeat дольше generationTimeoutMs + 5 секунд (обычно 125 секунд) переводятся в interrupted без потери сохранённого текста. Не используем массовую безусловную отмену на старте: она прервала бы живые потоки другого экземпляра. После аварии восстановление обычно занимает до 125 секунд + один минутный цикл.

Минутная очистка удаляет до 1000 просроченных сообщений, затем до 1000 истекших сессий без сообщений. Выборка по expiry-индексу, FOR UPDATE SKIP LOCKED позволяет нескольким процессам не ждать друг друга. При большом backlog физическое удаление может занять несколько циклов; логическая недоступность наступает строго по expires_at. Резервные копии/логи требуют отдельной политики хранения при деплое.

Если БД недоступна во время финального сохранения, сервер не объявляет несохранённый результат подтверждённым: клиент получает PERSISTENCE_ERROR, ресурсы потока закрываются, последняя успешно сохранённая generating-запись позже восстанавливается как interrupted.
