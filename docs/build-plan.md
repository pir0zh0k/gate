# План сборки ИИ-гейта

## Исходное состояние

На момент первоначального планирования в проекте был только AGENTS.md: исходный код, манифесты зависимостей и Git-репозиторий отсутствовали. Реализация ведется по рабочим этапам ниже; фактические проверки описаны отдельно в docs/testing.md.

## Обязательные правила

- Frontend: React 19, TypeScript, Tailwind, Feature-Sliced Design (FSD).
- Backend: Fastify, TypeScript, MVC.
- PostgreSQL в Docker с миграциями и индексами.
- Анонимная сессия в cookie, без отдельной страницы входа.
- Стриминговые ответы ИИ; история сессии сохраняется в БД.
- В контексте провайдера — последние 10 сообщений.
- localStorage используется как кеш истории, БД — источник истины.
- Строгая типизация: никаких any; внешние данные принимаются как unknown и валидируются.
- SOLID, DRY, KISS, YAGNI; переиспользование компонентов и логики.
- Минимальная документация каждого модуля в docs/.

## Предлагаемые решения

Это предложения, а не дополнительные требования AGENTS.md.

- Один репозиторий: apps/web, apps/api, packages/contracts, docs/.
- Общие контракты API и событий потока без зависимостей от UI, БД или секретов.
- Один диалог на анонимную сессию для первого релиза. Мультичат не добавлять без отдельного требования.
- Поток через POST-запрос и чтение response body; формат событий определить в общих контрактах.
- Один первоначальный ИИ-провайдер за небольшим интерфейсом адаптера; без лишней системы плагинов.
- Frontend и API доступны с одного origin; в разработке использовать проксирование.

## Этапы

### 1. Каркас и инструменты

- Предлагаемый менеджер пакетов — pnpm; перед установкой проверить совместимость версий. Провайдер согласован: OpenAI API, модель `gpt-5.6-terra`.
- Создать workspace и манифесты; зафиксировать зависимости lock-файлом.
- Настроить строгий TypeScript, lint, форматирование и тесты.
- На frontend создать необходимые FSD-слои: app, pages, features, entities, shared. Не добавлять пустые слои ради структуры.
- На backend разделить маршруты, контроллеры, прикладные сервисы, модели/репозитории и интеграции. Роль представления MVC выполняют JSON-ответы и события потока.
- Добавить шаблон переменных окружения без секретов, валидацию конфигурации и Docker Compose для PostgreSQL с volume и healthcheck.

Критерий: установка зависимостей, typecheck, lint и сборка каркаса проходят.

### 2. Данные и анонимная сессия

- Создать таблицы sessions и messages с миграциями, внешними ключами и временными метками.
- В messages хранить роль, текст, статус генерации и монотонный порядковый номер внутри сессии.
- Добавить уникальные ограничения для токена сессии и пары (session_id, sequence); индекс истории по (session_id, sequence).
- Создавать анонимную сессию при первом обращении, выдавать непрозрачный случайный токен в HttpOnly cookie; в production — Secure, явно выбранный SameSite.
- Проверять срок действия и принадлежность истории сессии на каждом запросе. Не принимать session_id из клиента как доказательство доступа.
- Проверять origin запросов, ввод и ограничения размера; добавить ограничение частоты генераций.

Критерий: новая сессия создается без формы входа, перезагрузка сохраняет ее, чужая история недоступна.

### 3. API истории и генерации

- Описать общие схемы запросов, ошибок и событий потока; валидировать внешние данные во время выполнения.
- Реализовать получение истории с курсорной пагинацией.
- Сохранять пользовательское сообщение до обращения к провайдеру.
- Для контекста выбирать до 10 последних завершенных сообщений в хронологическом порядке, включая текущий запрос пользователя. Системная инструкция не считается сообщением истории.
- Исключать ошибочные и незавершенные ответы из контекста. Уточнить допустимую для выбранного провайдера последовательность ролей без расширения лимита 10 сообщений.
- Не допускать параллельной генерации внутри одной сессии; использовать серверное ограничение, а не только блокировку кнопки.
- Добавить идемпотентность отправки, чтобы повтор запроса после сетевого сбоя не дублировал сообщение.

Критерий: история изолирована, порядок стабилен, лимит контекста соблюдается, повтор запроса не создает дубликатов.

### 4. Стриминговая интеграция с ИИ

- Реализовать интерфейс адаптера и подключить одного согласованного провайдера. Ключи хранятся только на сервере.
- Определить события начала, фрагмента текста, завершения и ошибки; добавить идентификатор сообщения.
- Создавать запись ответа со статусом генерации; сохранять накопленный текст периодически и по завершении, не на каждый токен.
- На обрыв клиента, таймаут и ошибку провайдера сохранять частичный текст и конечный статус; прерывать upstream-запрос, когда это поддерживается.
- При аварийном завершении сервера переводить оставшиеся записи генерации в прерванное состояние при восстановлении.
- Не держать транзакцию БД открытой во время сетевого потока. Обработать backpressure и очистку ресурсов.

Критерий: реальный ответ появляется по частям; полный или частичный результат и статус сохраняются, сбой не оставляет бесконечно активную генерацию.

### 5. Интерфейс и кеш

- После инициализации сессии показывать экран диалога с формой запроса без отдельной страницы авторизации.
- Реализовать список сообщений, ввод и отправку, потоковое обновление, отмену запроса и понятные состояния загрузки/ошибки.
- Выделять переиспользуемые компоненты только при реальной необходимости.
- Привязать localStorage-кеш к публичному идентификатору сессии, не сохранять там токен cookie.
- Версионировать и валидировать кеш, обрабатывать поврежденные данные и недоступность localStorage; очищать кеш при смене сессии.
- Показывать кеш как предварительную историю и сверять его с сервером, не выдавая незавершенный локальный ответ за сохраненный.
- Проверить клавиатурную доступность, адаптивность и поведение прокрутки во время потока.

Критерий: отправка работает без входа, ответы поступают по частям, перезагрузка восстанавливает серверную историю, поврежденный кеш не ломает интерфейс.

### 6. Проверки

- Unit: контекст из 10 сообщений, схемы, разбор потока, логика кеша.
- Integration с PostgreSQL: миграции, сессии, изоляция, пагинация, идемпотентность, статусы и параллельные запросы.
- Integration потока: успешный ответ, ошибка до/после первого фрагмента, таймаут, отмена и разрыв соединения. В автоматических тестах допустим контролируемый тестовый адаптер.
- E2E: первый визит → отправка → поток → перезагрузка → восстановление истории.
- Отдельная ручная проверка реального выбранного провайдера; тестовый адаптер не заменяет эту проверку.
- Выполнить lint, typecheck, тесты и production-сборку обоих приложений.

Критерий: проверки проходят, а реальная интеграция подтверждена без публикации ключей.

### 7. Документация и готовность к запуску

Документацию писать вместе с соответствующими модулями, не откладывать до конца:

- docs/architecture.md — структура и границы модулей.
- docs/database.md — схема, индексы и миграции.
- docs/session.md — cookie, срок действия и изоляция.
- docs/api.md — маршруты, ошибки и потоковый протокол.

- docs/frontend.md — FSD, UI-состояния и кеш.
- docs/development.md — установка, окружение, команды, проверки и запуск.

Добавить обработку завершения процесса, healthcheck API и безопасное логирование без токенов, ключей и содержимого сообщений по умолчанию.

Критерий: проект можно поднять по документации с новой БД; миграции применяются, API и frontend собираются, сквозной сценарий подтвержден.

## Согласованные решения

1. Пользователь выбрал ChatGPT, модель `GPT-5.6-terra`. Серверная интеграция — OpenAI API; официальный API-идентификатор модели: `gpt-5.6-terra`. Доступ конкретного API-проекта проверить при подключении, ключ нужен только на сервере.
2. Дизайн-референс: https://chatgpt.com. Адаптировать интерфейс под один анонимный диалог, не добавляя функции референса вне границ первого релиза.
3. Один диалог на анонимную сессию.
4. Срок жизни сессии — 1 час. Срок хранения истории — 6 часов.

Официальная документация модели: https://developers.openai.com/api/docs/models/gpt-5.6-terra.

## Уточнения перед реализацией

- Срок хранения истории подтвержден: 6 часов. От какой точки отсчитывать срок хранения — уточнить; до подтверждения предлагаем от создания сообщения.
- Сессия истекает через час после создания или после последней активности? До подтверждения предлагаем фиксированный срок от создания.
- После истечения сессии история остается в БД до срока удаления, но старая cookie больше не дает доступа. Восстановление доступа к старому диалогу не входит в первый релиз без отдельного требования.

## Границы первого релиза

Без аккаунтов, мультимодальности, загрузки файлов, RAG, биллинга и выбора множества провайдеров в UI, если они не будут запрошены отдельно.

## Порядок реализации: рабочие этапы

Ниже — последовательность реализации, а не отчет о выполнении. Тесты и документацию добавлять в каждом этапе: сначала воспроизводимый падающий тест поведения, затем минимальная реализация и проверка. Не откладывать все тесты до завершения разработки.

### Этап A. Основа репозитория

- Создать workspace с apps/web, apps/api и packages/contracts; Git инициализировать без коммитов и push.
- Предлагаемые инструменты: pnpm, Vite для web, Vitest для модульных тестов, Playwright для E2E. Конкретные версии проверить перед установкой.
- Создать конфигурации TypeScript, ESLint, форматирования и корневые команды проверки.
- Создать docker-compose.yml для PostgreSQL, шаблон окружения без значений секретов и docs/development.md.
- Подготовить frontend и backend к одному origin.

Готовность: зависимости устанавливаются, оба приложения собираются, проверки каркаса проходят. Локальные dev/preview-серверы не запускать без отдельного запроса пользователя.

### Этап B. Контракты и схема хранения

- Определить роли сообщений, статусы ответа, запрос отправки, страницу истории, ошибки и события потока.
- Предлагаемые маршруты: POST /api/session, GET /api/messages, POST /api/messages/stream, GET /api/health.
- Выбрать один механизм миграций и доступа к PostgreSQL; не вводить несколько конкурирующих слоев.
- sessions: внутренний ID, публичный ID, хеш секретного токена, время создания и истечения.
- messages: ID, session_id, sequence, role, content, status, request_id, created_at, expires_at.
- Индексы: уникальность токена, порядок сообщений внутри сессии, сроки удаления. Уникальность request_id ограничить пользовательскими запросами, чтобы ответ мог ссылаться на тот же запрос.
- Сессии не удалять каскадом при истечении часа: сообщения должны сохраняться в течение согласованных 6 часов.

Готовность: миграции применяются на чистой тестовой БД; ограничения порядка, ссылок и дубликатов проверены тестами.

### Этап C. Первый сквозной сценарий — сессия и история

- Реализовать создание и проверку анонимной сессии, cookie и получение истории.
- Подключить страницу диалога: первый визит создает сессию и показывает форму.
- Проверить сохранение сессии при перезагрузке и изоляцию двух независимых клиентов.
- При истечении сессии показать понятное состояние и начать новый диалог без доступа к старой истории.

Готовность: браузер → API → PostgreSQL работает для сессии и истории без ИИ-интеграции.

### Этап D. Отправка запроса и реальный поток

- Сохранить запрос, сформировать контекст из максимум 10 сообщений и создать запись ответа.
- Подключить OpenAI API через небольшой адаптер; модель задается серверной конфигурацией.
- Проверить доступ проекта к gpt-5.6-terra реальным запросом, когда доступен ключ. Отсутствие ключа не блокирует остальные этапы, но блокирует подтверждение реальной интеграции.
- Передавать контекст явно; не подключать скрытую провайдерскую историю, обходящую ограничение 10 сообщений.
- Привести события провайдера к собственным событиям start, delta, done, error.
- Подключить чтение потока на frontend и обновлять один ответ, а не создавать сообщение на каждый фрагмент.
- Сохранить окончательный текст и статус, проверить восстановление после перезагрузки.

Готовность: пользователь получает реальный ответ по частям, оба сообщения сохраняются в PostgreSQL.

### Этап E. Надежность и безопасность

- Добавить идемпотентность, серверную защиту от одновременной генерации, ограничения размера и частоты запросов.
- Обработать таймаут, отмену, разрыв потока, ошибку до первого фрагмента и ошибку после частичного ответа.
- Периодически сохранять накопленный текст; после сбоя отмечать незавершенные ответы как прерванные.
- Зафиксировать правило истечения сессии во время генерации: новые запросы не принимаются; уже авторизованный поток может завершиться в пределах своего таймаута.
- Не выводить токены, ключи и содержимое переписки в логи по умолчанию.
- При добавлении Markdown не исполнять HTML из ответа, ограничить допустимые протоколы ссылок.

Готовность: тесты сбоев не обнаруживают потерянные статусы, дубликаты или доступ к чужой истории.

### Этап F. Интерфейс по референсу ChatGPT

- Сначала определить визуальные параметры: цвета, типографику, ширину диалога, отступы и поведение поля ввода.
- Реализовать пустое состояние с формой и состояние диалога с закрепленным полем ввода.
- При одном диалоге не копировать список чатов, аккаунты, оплату, вложения и другие несогласованные функции референса.
- Добавить оформление сообщений, Markdown и блоков кода, отправку и остановку, сообщения об ошибках.
- Во время потока прокручивать вниз только если пользователь уже находится у конца переписки.
- Проверить мобильный экран, клавиатуру, видимый фокус и состояния доступности.

Готовность: UI последователен на desktop/mobile и не содержит неработающих декоративных кнопок.

### Этап G. Кеш и сроки жизни

- Реализовать версионированный кеш истории в localStorage с публичным ID сессии и сроками действия.
- Не показывать кеш старой сессии после ее истечения, даже если серверная история еще хранится.
- При запуске сверять предварительный кеш с ответом сервера; при отсутствии сети не выдавать кеш за подтвержденную активную сессию.
- На сервере сразу исключать просроченные сообщения из выдачи истории и контекста.
- Добавить периодическое пакетное удаление сообщений по expires_at и удаление истекших сессий без оставшихся сообщений. Индексы сроков удаления использовать в этой задаче.
- Разделить логическое истечение в 6 часов и физическую очистку по расписанию; документировать допустимую задержку очистки. Сроки резервных копий требуют отдельной политики при деплое.
- Проверить TTL тестовыми часами, не ожидая реальный час или шесть часов.

Готовность: истекшая сессия недоступна, просроченные сообщения не выдаются, кеш не раскрывает прошлый диалог, очистка удаляет просроченные записи.

### Этап H. Приемка

- Выполнить lint, typecheck, unit/integration, E2E и production-сборку.
- Подтвердить реальную ИИ-интеграцию, отдельно от тестового адаптера.
- Проверить сквозные сценарии: первый визит, поток, отмена, перезагрузка, новая сессия, истечение сроков, поврежденный localStorage, недоступный провайдер.
- Завершить документацию модулей и воспроизводимую инструкцию запуска с чистой БД.
- Не коммитить, не пушить и не разворачивать приложение без отдельного запроса.

Готовность: приложение работает по согласованному сценарию, проверки реально выполнены, известные ограничения перечислены.

### Рабочие предположения для сроков

До отдельного подтверждения: сессия живет 1 час от создания, каждое сообщение хранится 6 часов от своего создания. Это рабочие предположения, не дополнительные согласованные требования. После часа старый диалог недоступен клиенту, но остается в БД до очистки.
