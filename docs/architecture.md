# Архитектура

## Границы

`apps/web` (React/FSD) → same-origin `/api` (Fastify/MVC) → PostgreSQL и OpenAI.

`packages/contracts` содержит только схемы внешних данных, типы сообщений/событий и ограничения продукта. Не импортирует БД, SDK провайдера и UI. Входящие значения проходят проверку runtime-схемами, а не только приведением TypeScript-типа.

Frontend не получает API-ключ и секрет сессии. Сервер получает HttpOnly cookie, ищет ее хеш в PostgreSQL и проверяет срок действия. Публичный ID используется для кеша и отображения, но не дает доступ к данным.

## Состояния диалога

Инициализация сессии → загрузка истории → готовность → отправка → поток → завершение/ошибка/отмена. Истечение сессии прекращает доступ к прошлому диалогу; новый диалог использует новый идентификатор и отдельный кеш.

Сообщение пользователя сохраняется до вызова провайдера. Ответ создается в состоянии `generating`, обновляется накопленным текстом и заканчивается как `complete`, `error` или `interrupted`. Долгая сетeвая генерация не удерживает транзакцию PostgreSQL.

## Поток

Браузер делает POST с текстом и requestId. API возвращает NDJSON: отдельный JSON на строку. Виды событий: `start`, `delta`, `done`, `error`. Транспорт от OpenAI преобразуется на сервере; браузер не зависит от SDK или схем провайдера.

Модель получает явный контекст максимум из 10 сообщений; предыдущие provider response IDs не используются для скрытого расширения истории. Вызов не просит провайдера хранить ответ (`store: false`). Это не заменяет условия обработки данных самого провайдера.

## Источник истины и сроки

PostgreSQL — источник истины; localStorage — необязательный кеш. UI не показывает кеш до подтверждения активной сессии сервером. Серверное время используется для учета разницы часов браузера.

Рабочие предположения: срок сессии 1 час от создания; срок сообщения 6 часов от создания. Логически просроченные сообщения сразу исключаются из выдачи и контекста; физическое удаление выполняется периодически. Истечение сессии не означает немедленное каскадное удаление истории. Резервные копии требуют отдельной политики хранения при деплое.

## Проверки и эксплуатация

Тесты добавляются вместе с поведением: unit для контрактов, контекста и потока, integration на отдельной реальной PostgreSQL, E2E в браузере. Тестовый провайдер проверяет управляемые сценарии ошибок и не является production fallback.

Проверка реального OpenAI требует серверного ключа и доступа API-проекта к выбранной модели. Без этого нельзя заявлять, что реальная интеграция подтверждена.

В production необходимы HTTPS, точный APP_ORIGIN, надежные серверные секреты и ограничение доступа к PostgreSQL. Только локальные инструменты и тесты не заменяют деплой и эксплуатационную проверку.
